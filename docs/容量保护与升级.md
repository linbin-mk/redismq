# 容量保护与存储升级

## 容量与背压

所有限制由 Redis 脚本在同一队列的原子操作中检查，多生产者不能突破限制：

| 限制 | 默认值 | 达到限制后的行为 |
|---|---:|---|
| 正文条数 `max-queue-size` | 100000 | `MQ_QUEUE_FULL` |
| 正文合计 `max-queue-bytes` | 67108864 | `MQ_QUEUE_BYTES_FULL` |
| 单条 JSON UTF-8 大小 `max-message-bytes` | 65536 | Java 序列化时提前拒绝；脚本再次校验 |
| 防重条数 `max-dedup-entries` | 200000 | `MQ_DEDUP_FULL` |
| 命名空间队列目录 `max-registered-queues` | 1024 | `MQ_DIRECTORY_FULL` |

死信和处理中正文都占用条数及字节额度。ACK、取消、删除死信会释放正文额度，完成编号继续占用防重额度直到保留窗口结束。消息正文存续期间，其编号的防重位置被预留，不会因过期清理丢失；同一请求在队列或索引已满时仍可幂等重试。业务去重命中的新请求编号也占用一条防重额度，避免用无限随机请求编号拉大索引。

防重容量至少需要覆盖：活跃消息编号 + 完成速率 × 编号保留时长 + 业务去重键 + 重复请求别名。默认 20 万条与 24 小时窗口并不适用于持续每秒上千条的完成量；根据业务允许的防重窗口缩短保留时间或调整容量。索引满后应有界退避或业务降载，不能不断生成新编号立即重试；不会静默驱逐有效防重记录。

字节额度只统计 JSON 正文，不含元数据、失败原因、索引和 Redis 分配器开销。用 `stats().payloadBytes()` 与 `stats().dedupEntries()` 观察实际占用；为整个 Redis 实例设置 `maxmemory` 和 `maxmemory-policy noeviction`，并预留其他业务、元数据及复制缓冲区的内存。多个队列的合计预算由宿主应用规划；本组件不修改宿主 Redis 配置，也不提供跨槽全局内存事务。Redis 拒绝写入时向调用方抛出异常，发送超时继续用原编号重试。发送中的过期索引查询保持只读，首个写操作是受 OOM 检查的 HSET；不能提前 HDEL / ZREM，否则兼容模式 Lua 可能绕过 maxmemory。一次脚本刚开始时尚有余量，写入后仍可能略超 maxmemory，因此必须为脚本、处理中元数据和客户端缓冲预留额外内存。这与 [Redis 官方说明的 Lua OOM 语义](https://redis.io/docs/latest/develop/programmability/eval-intro/) 一致，本轮在专用容器中另有真实耗尽内存的回归验证。

## 单次执行的工作上限

- 领取最多 16 条，正文合计最多 64 KiB，使用 RESP 返回正文，避免在 Redis 重新编码大 JSON。
- 每次领取最多恢复 8 个过期处理权，每次发送或领取最多清理 32 条过期防重记录。
- `deadMessages()` 的完整正文页最多 64 KiB；按实际返回条数推进 offset，直到空页。`messages()` 元数据分页保持正常数量语义，适合看板使用。
- 旧数据迁移每次至多 10 条，累计旧记录达到 64 KiB 时提前结束；至少处理一条。
- 续期、ACK、重试和监控列表只解析小元数据，不读写正文。脚本用 SHA 缓存调用，目标节点丢失缓存后自动恢复。
- 每个消费者仅领取空闲工作槽能够处理的消息；已取消续期和超时任务立即从调度队列移除；最长执行时间使用独立调度线程，不受 Redis 续期调用阻塞影响。

这些上限控制单次脚本工作量；实际延迟仍受 Redis 主机、数据规模、其他命令及网络影响，不能保证任意环境绝无慢日志。不要向共享 Redis 投放无界数量的队列或采用无限立即重试。

## 从原内联正文格式升级

新格式为版本 2，原 `messages` 哈希保存元数据，新增 `payloads` 哈希和 `payload-bytes` 计数键；固定键清单可由 `storageKeys()` 获取。原有键名称不变，新客户端兼容读取和消费版本 1 消息。

升级必须先停止同一命名空间下的所有旧生产者和消费者；迁移期间也暂停新消费者和管理写入，保证索引分页稳定。旧版本不认识分离正文，不能混用，迁移后不能直接降级。命名空间内包含冒号的旧队列名应先用旧版本排空或显式迁移至不含冒号的新队列名；新版本拒绝含冒号的队列名，防止命名空间与队列名称拼接冲突。

迁移不会删除消息，不改变投递次数、索引顺序或处理权期限，可重复运行。示例：

```java
for (MessageState state : MessageState.values()) {
    int offset = 0;
    while (true) {
        int checked = mq.migrateStorage("task-execution", state, offset, 10);
        if (checked == 0) break;
        offset = Math.addExact(offset, checked);
        // 可按运维负载在批次间限速；不要并发修改该队列。
    }
}
```

中断后可以从零重新运行，不会重复累计字节。每个已知队列均需迁移。迁移完成后检查各状态数量、正文详情和统计，再启动新生产者和消费者。迁移如遇既有容量超标，不删除旧数据；新发送会持续拒绝，待消费、处理死信或调整预算后恢复。

当正文中仍有版本 1 内联记录时，新发送返回 `MQ_STORAGE_UPGRADE_REQUIRED`，防止漏算存量字节；同一编号的重复请求仍可返回原结果。也可用旧版本先排空所有消息，再切换新版本，从而不需要迁移。新队列无需迁移。

不要手工删除计数键、给固定键设置 TTL，或用缓存淘汰策略回收 MQ 键。检测到计数缺失、非法计数或正文丢失时会拒绝相关操作，避免把损坏数据当成成功消息。Lua 出错不具备事务回滚能力，Redis ACL 应完整允许组件涉及的脚本及哈希、有序集合、计数命令；Pub/Sub 权限可缺省，消费者会回退到轮询。

## dailyForServer 接入

已只读核对目标项目：Spring Boot 3.5.16、Redisson 3.52.0 与本组件一致，Java 25 可以使用本组件的 Java 17 字节码。目标项目当前依赖使用 `com.mk:redis-mq-dashboard:0.1.0`，本仓库实际 Maven groupId 为 `io.github.linbin-mk`；接入时应修正依赖坐标并采用 `0.2.0` 构件。这里没有修改或发布目标项目。

复用目标项目现有 `RedissonClient`，从其已有配置来源提供 `redis-mq.*` 参数。业务处理必须幂等，外部调用必须设置超时。根据实际任务量、Redis 内存和可接受的防重窗口设置容量，先在目标环境验证重启恢复、复制切换和业务幂等，再进入正式流量。

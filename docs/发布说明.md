# 发布到 Maven Central

项目使用 Sonatype Central Portal 发布，命名空间为 `io.github.linbin-mk`，Java 包名仍为 `com.mk.mq`。
日常发布推荐使用 GitHub Actions：推送 `v0.4.0` 这样的版本 tag 后，自动构建、测试、签名并公开发布。
账号和发布凭证只需初始化一次，本机不需要安装 GPG 或执行 Maven 发布命令。

配置文件存在不代表版本已经公开；以 Maven Central 实际可下载的版本为准。

## 1. 配置 GitHub Secrets

使用 GitHub 账号登录 [Central Portal](https://central.sonatype.com/)，确认 `io.github.linbin-mk` 为 `Verified`。
在 [User Token 页面](https://central.sonatype.com/usertoken)生成并保存 Token Username 和 Token Password。

打开 [仓库 Actions Secrets 设置](https://github.com/linbin-mk/redismq/settings/secrets/actions)，进入：

`Settings → Secrets and variables → Actions → New repository secret`

先添加三个仓库 Secret：

| Name | Value |
|---|---|
| `CENTRAL_USERNAME` | Central Token 的 Username |
| `CENTRAL_PASSWORD` | Central Token 的 Password |
| `GPG_PASSPHRASE` | 新生成并保存在密码管理器中的随机私钥口令，至少 20 个字符 |

这些值不应写入 Git、聊天、截图或命令行参数。本地 `settings-local.xml` 已排除 Git 提交，但它不会自动传到 GitHub。
Central Token 过期后，在 Portal 生成替代 Token，再更新上面两个 Secret。

## 2. 在 GitHub 生成一次签名密钥

先将 `.github/` 中的工作流、根 POM、四个模块 POM 和相关文档提交并推送到默认分支 `master`。
普通分支推送不会发布；密钥准备工作流只接受手动触发。

在仓库 `Actions` 页面选择 **Prepare Maven signing key → Run workflow**：

- `name`：例如 `linbin-mk`。
- `email`：填写可公开的维护者邮箱。姓名和邮箱会包含在公开密钥中。

工作流使用 GitHub 的 Ubuntu runner 自带 GPG，生成有效期一年的 RSA 3072 位签名密钥。
私钥受 `GPG_PASSPHRASE` 保护，公钥上传到 `keyserver.ubuntu.com`，供 Central 验证签名。

运行完成后，在该次运行页面的 **Artifacts** 下载 `redismq-signing-key-运行编号`。
这个备份在 GitHub 上只保留一天，包含：

- `gpg-private-key.asc`：受口令保护的私钥。
- `public-key.asc`：公钥。
- `fingerprint.txt`：完整密钥指纹。

把整个备份下载后保存在本机安全位置。用文本编辑器打开 `gpg-private-key.asc`，复制全部内容，
包括 `-----BEGIN PGP PRIVATE KEY BLOCK-----` 和结束行，作为第四个仓库 Secret：

| Name | Value |
|---|---|
| `GPG_PRIVATE_KEY` | `gpg-private-key.asc` 的完整文本 |

私钥文件与口令要分别安全保管；备份中的私钥仍属于敏感文件，不要提交到仓库。
下载确认并配置好 Secret 后，可以删除该次运行的备份 Artifact。
若最后的公钥上传失败，备份会先保存好；正式发布工作流也会再次上传同一公钥。

若已经有自己的签名密钥，可跳过生成工作流，直接配置对应的 `GPG_PRIVATE_KEY` 和 `GPG_PASSPHRASE`。
不要为每个版本重新生成密钥；密钥有效期将到时，需要延长有效期并更新私钥 Secret 和公钥服务器，或按需轮换。

## 3. 按 tag 自动发布

确认根 POM 版本、所有子模块的父版本和模块间显式依赖版本一致，例如 `0.4.0`。
将代码提交并推送到 GitHub，再执行：

```bash
git tag v0.4.0
git push origin v0.4.0
```

也可以在 GitHub 创建指向正确提交的 `v0.4.0` tag。
工作流由 tag 的 push 事件触发；对已经存在的 tag 创建 Release 不会重新触发。

**Publish to Maven Central** 工作流先在 Java 17 上分别验证 Redis 6.2 和 7.4，每个版本包含独立的 8 MiB OOM 实例和 MySQL 历史分析测试库；功能、并发和真实 OOM 测试全部通过后才进入签名发布。随后会：

1. 核对 tag 与根 POM、所有模块的父坐标及版本一致，拒绝 SNAPSHOT 或不匹配的版本。
2. 在 Ubuntu runner 上使用 Java 17，导入签名密钥并生成 Maven 认证配置。
3. 将签名公钥上传到公钥服务器。
4. 运行现有测试，生成普通 JAR、源码包、Javadoc 包及 GPG 签名。
5. 上传父 POM 和四个组件，通过 Central 校验后自动公开发布，并等待状态变为 `PUBLISHED`。

CI 使用 `central.autoPublish=true` 和 `central.waitUntil=published` 覆盖 release profile 的本地默认值。
仓库和工作流只申请读取代码的 GitHub Token 权限；向 Central 发布使用专用 Token。

| artifactId | packaging |
|---|---|
| redis-mq-parent | pom |
| redis-mq-core | jar |
| redis-mq-spring-boot-starter | jar |
| redis-mq-dashboard | jar |
| redis-mq-dashboard-mysql | jar |

Central 的正式版本不能覆盖。后续修复要更新所有相关 POM 的版本，再推送新的 tag，例如 `v0.4.1`。
如果工作流在上传后超时或失败，先到 [Deployments](https://central.sonatype.com/publishing/deployments) 检查是否已经发布，避免重复上传同一版本。

## 4. 发布后引用

```xml
<dependency>
    <groupId>io.github.linbin-mk</groupId>
    <artifactId>redis-mq-spring-boot-starter</artifactId>
    <version>0.4.0</version>
</dependency>
```

MVNRepository 的收录不决定依赖是否可用，以 Maven Central 的实际下载结果为准。

## 可选：本地验证或发布

普通构建不需要签名工具或凭证：

```bash
mvn clean verify
```

验证发布附件生成，可跳过签名且不上传：

```bash
mvn -Prelease -Dgpg.skip=true clean verify
```

仍需本地发布时，可安装 GPG、导入或生成签名密钥，参考 `docs/settings-central.example.xml` 配置本地 `settings-local.xml`，再执行：

```bash
export GPG_TTY=$(tty)
mvn -s settings-local.xml -Prelease clean deploy
```

本地默认 `central.autoPublish=false`，通过校验后在 Portal 手动点击 Publish。CI 会覆盖为自动发布。

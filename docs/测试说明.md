# 测试说明

## 默认验证

```bash
mvn clean verify
```

不连接 Redis，执行参数边界、Spring Boot 自动配置、客户端复用、监听器签名、看板认证、只读查询、分页和错误处理测试。集成测试和负载测试在未提供参数时显示为跳过；这不代表通过了真实 Redis 验证。

看板测试使用 JDK 动态代理作为客户端桩，Mockito 使用 subclass mock maker，避免 Java 25 环境中自动附加 agent 的依赖；没有降低产品的认证和只读检查。

## 真实 Redis 集成验证

创建专用、本机可回收的 Redis；下列名字与端口应确保未被占用：

```bash
docker run -d --name redis-mq-test -p 127.0.0.1:16379:6379 \
  --memory=384m --cpus=2 redis:7.4-alpine \
  redis-server --save '' --appendonly no \
  --maxmemory 256mb --maxmemory-policy noeviction \
  --slowlog-log-slower-than 1000 --slowlog-max-len 4096
mvn clean verify -Dmq.redis=redis://127.0.0.1:16379 -Dmq.load=true
```

此配置故意关闭持久化，仅用于隔离验收。也可将镜像改为 `redis:6.2-alpine` 验证最低支持版本。测试连接使用 `mq.redis` 显式传入，不要指向业务实例。

每次测试使用随机命名空间，结束时按固定完整键名删除测试键，不执行 KEYS、SCAN 或 FLUSHDB。核心集成测试覆盖：

1. 延迟、确认、防重、正文冲突、取消和改期。
2. 多消费者竞争领取、多生产者竞争容量；旧凭证无法确认、续期、重试或拒绝新领取。
3. 失败、超时、重试次数、死信、重放和删除；集中超时按批次恢复。
4. 条数、UTF-8 大小、正文总字节数、防重别名和队列目录的上限。
5. 防重过期清理、存续编号预留、满容量下的同编号重试。
6. 大正文领取和死信正文分页的字节预算；元数据不包含大正文。
7. 只读查询不恢复过期处理权；类型冲突、正文缺失和计数损坏不会作为成功消息处理。
8. 旧格式有界、可重复迁移；SCRIPT FLUSH 后自动恢复缓存。
9. 自动续期、独立处理时限和强制停机后迟到回调不能确认。

`-Dmq.load=true` 额外开启 8 生产线程、8 消费工作槽、4,000 条 1 KiB 消息的完整 Java API 负载测试，验证无消息丢失、无重复回调、ACK 后正文计数归零、取消的定时任务不滞留。输出 `MQ_LOAD` 行记录本机实际吞吐，属于该次样本，不能作为生产容量承诺。

## 真实 OOM 回归

另外创建一个**专用空实例**，将 `maxmemory` 设为 8 MiB，用于刻意耗尽 Redis 内存；不要用功能测试或业务实例代替：

```bash
docker run -d --name redis-mq-oom-test -p 127.0.0.1:16381:6379 \
  --memory=128m --cpus=2 redis:7.4-alpine \
  redis-server --save '' --appendonly no --maxmemory 8mb --maxmemory-policy noeviction
mvn -pl redis-mq-core test -Dtest=RedisMqOomTest -Dmq.oom.redis=redis://127.0.0.1:16381
```

测试持续发送 64 KiB 正文，要求在 512 条以内遇到 Redis 内存拒绝，校验被拒请求未留下孤立正文或错误计数、同编号仍能防重返回、新别名被拒绝，以及 OOM 时仍能领取已有积压并通过 ACK 释放空间。允许把 `mq.oom.redis` 参数与完整 verify 命令合并。该测试专门防止 Lua 先执行删除后绕过 Redis OOM 检查的回归。

## 脚本性能对比

在集成测试结束后单独运行；集成测试会清理脚本缓存，不要同时压测同一实例。

```bash
python3 scripts/benchmark-redis.py --port 16379 --output /tmp/redis-mq-benchmark.json
```

对比原版时，将修改前的 `queue.lua` 保存为独立文件，并加上 `--baseline /tmp/original-queue.lua`。脚本使用标准库，不需要安装 Python Redis 包；只连接显式指定的本机端口，只读查询 CONFIG，不修改 Redis 配置。使用随机队列键，结束后 UNLINK 精确清理。

场景为 10,000 条 1 KiB 消息及 1,000 条 64 KiB 消息，正文包含高比例 JSON 转义字符；每条领取后执行一次续期和一次确认。记录实际交付数量、批次大小、客户端延迟、串行场景吞吐和按本轮队列过滤的 Redis 慢日志。短批次持续领取直到空队列，不能把返回少于请求数量当作结束。

慢日志阈值为容器启动时设置的 1 毫秒；零条慢日志表示没有超过阈值的该操作，并不表示其耗时为零。客户端延迟包含网络、Docker 和 Python 编解码开销。不要把串行诊断场景的吞吐当成并发 Java API 的上限。

本轮测量与已知限制见 [Review 验收报告](review-20261108/验收报告.md)，存储格式升级见[容量保护与升级](容量保护与升级.md)。

## 验证范围

本机 Docker 覆盖单节点 Redis 6.2 与 7.4。持久化断电恢复、复制切换、Redis Cluster、网络分区、服务端时钟变化和生产共用 Redis 的资源争用需在实际部署拓扑验证。所有回调仍需业务幂等和外部调用超时，组件不提供 exactly-once 或跨业务数据库的原子事务。

## 发布前检查

执行 `mvn clean verify` 生成构件，核对三个组件 JAR 中的 `META-INF/LICENSE`、`META-INF/NOTICE`、Lua 和看板资源。源码包不包含 `.git`、`target`、日志、本机配置或连接凭据。发布新的存储格式应使用新版本号，不覆盖已发布的 `0.1.0`；发布和目标应用变更独立执行。

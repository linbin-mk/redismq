# Redis MQ Review 验收报告

日期：2026-11-08。对比基线：本仓库 `98a54c6`。本报告记录发布前的本机验收结果；对应修复纳入 0.2.0，后续发布记录见 [CHANGELOG](../../CHANGELOG.md)。未修改 dailyForServer。

## 已修复的问题

| 问题 | 修复后的行为 |
|---|---|
| 正文仅按条数限制，默认最坏可累积约 6.1 GiB | 增加每队列 64 MiB 正文总额，包含处理中和死信；并发发送原子检查 |
| 防重索引和业务去重新编号别名无容量上限 | 增加防重条数上限，不驱逐有效记录；正文存续期间为完成后的编号预留防重位置 |
| 发送前删除过期索引会绕过兼容模式 Lua 的 OOM 检查 | 所有发送前置检查保持只读，首个写入是会触发 OOM 拒绝的 HSET；真实内存满回归覆盖两种 Redis 版本 |
| 大正文在领取、续期和状态更新中重复 JSON 解码、编码、复制 | 正文与元数据分离，正文通过 RESP 返回；每次领取至多 16 条、正文至多 64 KiB |
| 集中超时和过期清理叠加大量写操作 | 每次最多恢复 8 条处理权、清理 32 条防重记录；不扫描全库 |
| 快速回调取消的定时任务滞留调度队列 | 开启 remove-on-cancel，端到端测试直接检查续期和时限调度队列最终为空 |
| 最长执行时间依赖续期间隔，可能迟到数十秒 | 使用独立的时限调度线程；防止迟到中断影响被复用的工作线程 |
| 队列名与命名空间中的冒号可能组合成相同 Redis 键 | 队列名拒绝冒号，命名空间和消息编号仍可使用；升级说明包含旧名称处理方式 |
| 队列目录和本机登记缓存可以随动态队列数量增长 | 命名空间目录默认上限 1024，脚本原子登记 |
| 每次传输完整 Lua，重连后缓存可能丢失 | EVALSHA 调用，NOSCRIPT 自动回退 EVAL 并恢复目标节点缓存 |
| 先构造任意大的 JSON 字符串才检查消息大小 | UTF-8 序列化过程中限制字节数；不继承宿主 ObjectMapper 的默认多态类型解析 |

同时增加正文计数损坏、正文缺失、毫秒精度和配置边界检查。监控继续只读；`stats()` 增加正文实际字节和防重记录数量。

## 功能与资源验证

使用本机 Docker Desktop、Java 25.0.4.1、Java 17 编译目标。功能实例限定 2 CPU；Redis 7.4.12 使用容器 384 MiB、maxmemory 256 MiB，Redis 6.2.24 使用容器 256 MiB、maxmemory 128 MiB；均为 noeviction，关闭持久化，仅作测试。

每个版本另外使用独立的 maxmemory 8 MiB、容器 128 MiB 实例验证 OOM。初次复现时，旧发送顺序可在 8 MiB 的 maxmemory 下继续增长到 14,810,024 字节；修复后新写入被拒绝，重复请求不新增记录，已有消息可继续领取并确认。测试检查被拒请求没有遗留孤立正文或错误字节计数。单次脚本从尚有空间开始执行后可能略超 maxmemory，不能将 maxmemory 当成进程 RSS 的硬上限，需额外预留运行内存。

最终命令：

```bash
mvn -o clean verify -Dmq.redis=redis://127.0.0.1:16379 -Dmq.load=true -Dmq.oom.redis=redis://127.0.0.1:16381
mvn -o clean verify -Dmq.redis=redis://127.0.0.1:16380 -Dmq.load=true -Dmq.oom.redis=redis://127.0.0.1:16382
```

两个版本分别通过 38 项测试，失败、错误、跳过均为零：22 项核心集成、3 项参数边界、1 项端到端负载、1 项真实 OOM、4 项 starter 和 7 项 dashboard 测试。

| 完整 Java API 负载 | Redis 6.2.24 | Redis 7.4.12 |
|---|---:|---:|
| 8 生产线程、8 消费槽、1 KiB 正文 | 4000 条 | 4000 条 |
| 本轮处理速率 | 770.3 条/秒 | 824.1 条/秒 |
| 重复回调 | 0 | 0 |
| 完成后未处理正文 / 正文字节 | 0 / 0 | 0 / 0 |
| 完成后取消任务残留 | 0 | 0 |
| 8 MiB OOM 实例接受的 64 KiB 消息数 | 89 | 79 |

接受条数随 Redis 基础内存和分配开销变化，不是产品容量参数。负载速率包含本机 Docker 网络、JSON、通知、业务调度和 ACK 的全部开销，仅代表这次样本；至少一次投递在宕机等条件下仍允许重复。

三个模块构建成功，JAR 包含 LICENSE、NOTICE，核心 JAR 中两份 Lua 与当前源码逐字节一致；Python 压测脚本通过语法检查，`git diff --check` 通过。无 Redis 参数的默认 `mvn -o verify` 也已通过。确认四个活动测试实例均无残留键后，已删除本轮创建的全部五个测试容器；既有容器未改动，下载的 Redis 镜像保留供后续复测。

## 性能对比

独立执行 [benchmark-redis.py](../../scripts/benchmark-redis.py)，原始结果在 [benchmark.json](benchmark.json)。同一 Redis 7.4.12 实例、2 CPU、1 毫秒慢日志阈值；使用高转义 JSON，分别发送并完整处理 10,000 条 1 KiB 和 1,000 条 64 KiB 消息，每条执行领取、一次续期和确认。

| 本轮最终样本 | 修改前 | 修改后 |
|---|---:|---:|
| 1 KiB：领取脚本最长慢日志耗时 | 10.998 ms | 1.979 ms |
| 1 KiB：领取客户端 P99 | 16.394 ms | 3.910 ms |
| 1 KiB：串行诊断吞吐 | 404.8 条/秒 | 408.6 条/秒 |
| 64 KiB：领取脚本最长慢日志耗时 | 299.356 ms | 1.048 ms |
| 64 KiB：领取客户端 P99 | 450.168 ms | 4.459 ms |
| 64 KiB：续期超过 1 ms 的慢日志条数 | 1000 | 0 |
| 64 KiB：串行诊断吞吐 | 113.7 条/秒 | 209.1 条/秒 |

大正文领取脚本在本轮的最长阻塞降低约 99.65%，串行诊断吞吐提高约 1.84 倍。此前复测曾出现修改前约 1 秒的领取阻塞；主机调度会导致各轮最大值变化，因此交付文件固定记录最终这一轮，不选择更有利的混合样本。优化后仍有少量 1–3 ms 慢日志，不能声称任意负载下绝无慢查询。

零条慢日志只表示未达到 1 毫秒阈值，不表示操作耗时为零。客户端往返延迟包含 Docker、网络和 Python 开销；串行诊断吞吐不等于并发 Java API 上限。对比中每个版本均消费全部消息，短批次继续领取至空，不会提前结束。

## 接入与升级约束

- 新写入采用格式 2。旧数据可读取，但应停止旧生产者、消费者及管理写入，按状态有界迁移或先用旧版排空；不能混跑或直接降级。详见[容量保护与升级](../容量保护与升级.md)。
- 单条正文硬上限 64 KiB，死信正文页按实际返回条数推进 offset；元数据分页保持原数量语义。
- 全部实例应采用一致队列配置。防重容量需覆盖速率 × 保留时间、活跃编号、业务键和别名；满容量后需要业务退避或降载。
- Redis 需要 noeviction 和内存预算，固定 MQ 键不能设置 TTL；多队列、元数据、客户端缓冲和其他业务的合计内存由部署方规划。本轮不承诺任意主机或共享负载下零慢查询。
- 持久化断电恢复、Redis Cluster、复制切换、网络分区和生产资源竞争不在本机单节点验收范围。业务仍需幂等和外部调用超时。
- dailyForServer 的 Boot / Redisson 版本一致；其当前 `com.mk:redis-mq-dashboard` 坐标应改为本仓库实际 `io.github.linbin-mk`。本次修复纳入 0.2.0，不覆盖已发布的 0.1.0；目标项目与环境配置尚未修改。
